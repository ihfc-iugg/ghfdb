# Research: Check a workbook and get a report of every problem

**Spec**: [spec.md](spec.md) · **Decisions**: [decisions.md](decisions.md)

There is no `planning-notes.md` and no sketch for this feature. Every measurement below was taken
on 2026-11-05 against the field schema on `main`, with synthetic workbooks generated by
`UploadTemplate` and filled with valid values, then seeded with one problem of each kind.

## Running the checks

**Decision: Frictionless's own validation, on the values read from the workbook.**

Three ways were tried, each on the same seeded workbook.

| Approach | Seeded problems found | Notes |
|---|---|---|
| `frictionless.validate` on the `.xlsx` | all | Reads with openpyxl itself. 18.6 s for 20,000 children, of which 13.5 s is reading. Refuses an absolute path outside its base path unless `basepath` is given. |
| `frictionless.validate` on rows already read (`Resource(data=…)`) | all | 3.0 s for 20,000 children. Row numbers are positions in the data, so the check keeps the Excel row of each child beside them. |
| pandera, with `pandera.io.from_frictionless_schema` | not all | Validates whole columns in 0.7 s, but **accepts `3.5` in a whole-number field** (the coercion to a nullable integer truncates it, the defect Article XII forbids), reports each type failure twice (`coerce_dtype` and `dtype`), raises `TypeError` inside `in_range` on a column holding text, and reports a cell of spaces as wrong type. Every one of these would need code of ours around it. |

Frictionless, on the values, reports each seeded problem with the right kind: `type-error` for
`about 60`, `1,234.5`, `3.5` in an integer field, `True` in a number field and a date in a
year-and-month field. `constraint-error` names its constraint: `required`, `minimum`, `maximum`,
`maxLength`, `pattern` or `enum`. A number stored as text (`12.5`) and a whole number stored as
`3.0` are accepted, which is decision D-1. It is already a runtime dependency (ADR 0004), and the
field schema is already a `frictionless.Schema`, so the check passes it on as it is, with no
translation into another library's terms.

Each error maps to one problem kind:

| Frictionless error | Problem kind |
|---|---|
| `constraint-error`, constraint `required` | missing |
| `type-error` | wrong type |
| `constraint-error`, constraint `pattern` | wrong type (spec, Clarifications) |
| `constraint-error`, constraint `minimum`, `maximum` or `maxLength` | out of range |
| `constraint-error`, constraint `enum` | not in vocabulary |

Two gaps were found, both small:

- **Text `nan`, `inf` and `-inf` in a number field are accepted as numbers** (Python's `float()`
  reads them). `nan` then fails the range check as out of range, and `inf` passes a field with no
  range. Neither is what the assessor typed a number as, so the check reports both as wrong type,
  looking at the values Frictionless read rather than the text.
- **A cell of spaces only is a type error, not empty.** The spec reads it as empty (Edge Cases),
  so spaces-only cells are made empty before validation. That is the one change made to a value,
  and it changes nothing an assessor typed into a number or a term.

**Speed.** Validation is not this feature's target (R11). On rows already read, Frictionless's
row-by-row casting costs about 0.15 ms per child. The check's own code works on whole columns
(Article XIII). The loop is inside Frictionless, and the pull request says so.

## Reading the workbook

**Decision: openpyxl, already a runtime dependency, loaded once with `data_only=True`.**

- `data_only=True` gives the value Excel last saved for a formula cell and never evaluates the
  formula (Article V, FR-013). A formula cell saved by a program that does not calculate has no
  saved value and reads as empty, which is the spec's edge case.
- openpyxl reads 20,000 children in 13.5 s. python-calamine reads the same in 2.0 s and is
  established, but the spec sets no speed target (existing-first, step 1), so it is not added.
  It is the first thing R11 should measure.
- openpyxl warns "Data Validation extension is not supported and will be removed" on the
  hand-maintained template. That concerns choice lists, which the check never reads, and the
  original is never written, so the warning is silenced for that one message.
- `.xlsx` and `.xlsm` are read. An `.xls` file, which openpyxl cannot open, is a could-not-run
  error naming the file.

**Finding the header and the data.** The hand-maintained template (`tests/sources/upload-template.xlsx`)
and the generated one both put `ID` and the field codes in row 1 and seven description rows under
it, labelled in column A: Obligation, Domain, Quality Relevance, Name, Short Name, Unit, Allowed
range of values (`ghfdb.template.ROW_LABELS`). The check:

1. takes as the header the first row, of the first 20, in which most non-empty cells name a
   field, by code, published column name or earlier column name (FR-009);
2. skips every row directly under it whose column A holds one of the description row labels,
   compared without regard to case or surrounding spaces, so a workbook with more, fewer or no
   description rows reads the same (FR-008, decision D-4);
3. reads every later row as a child, except a row whose only filled cell is `ID`, or none
   (FR-008).

The field schema's `earlierColumnNames` already holds the two renamed columns (`tc_pT_fuction`,
`Ref_ISGN`), so recognising an earlier template's columns needs no new data.

## Writing the report copy

**Decision: openpyxl, writing into the workbook it loaded and saving it under the report name.**

- Writing into the loaded workbook keeps every sheet, value and column the assessor knows, so
  each problem can be shown in the cell it is about.
- Measured at 31 s to load and save 20,000 children, against 9 s for python-calamine with
  XlsxWriter. The second builds a new file, so every sheet of the original would have to be
  rewritten by our code. Not worth it with no speed target.
- Because the workbook was loaded with `data_only=True`, formulas reach the report copy as their
  saved values. That is what was checked, so it is what the report shows (decision D-5).
- The report copy is always `.xlsx`, named `<name>.report.xlsx` beside the workbook. Saving
  replaces an earlier report copy (FR-002). A report copy that is open in Excel cannot be
  replaced on Windows; the `PermissionError` becomes a could-not-run message.

## Suggestions

**Decision: the standard library's `difflib.get_close_matches`, with `n=1`.** Values and terms
are compared after removing square brackets and surrounding spaces and folding case, so
`Core samples`, `[core samples]` and `[Core sampels]` all suggest `[Core samples]`. When the
comparison finds an exact match after that normalising it is the suggestion, otherwise the one
closest term above a cutoff of 0.8 (`difflib`'s ratio). No package was needed: rapidfuzz does the
same faster, and speed is R11's.

## The vocabulary release

The vocabulary files carry no version number. Every concept scheme names the release it belongs
to with `dcterms:isPartOf`, for example `https://doi.org/10.5880/fidgeo.2026.065`. The report
copy names the release, or releases, the schemes read for this check are part of, read from the
graphs `Vocabularies` already holds after `load_schema`. Offline use (FR-014) already works:
`caching_session` keeps every downloaded file and uses it when the server cannot be reached
(`stale_if_error=True`). With nothing cached and no network, `load_schema` raises `OSError`,
which becomes the could-not-run message.

## Several values in one cell

Three fields have a separator (`C25`, `C26`, `C49`), and all three constrain only the cell's
length, which applies to the cell as a whole. No field with a separator has a vocabulary or a
pattern today, so scenario 1.10 changes nothing for the current schema. The plan meets it in the
one place it can matter: a field that has a separator and a vocabulary or a pattern has each value
checked on its own, with Frictionless's own field reader, and is tested with a test schema.

## The command line

**Decision: `argparse`, as `ghfdb check <workbook>`**, with an entry point in `[project.scripts]`.
The standard library does the whole job for one subcommand and one argument. Exit statuses: `0`
no problems, `1` problems found, `2` could not run, which is also what `argparse` uses for a
usage error.
